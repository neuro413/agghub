轻量化 LLM 渠道聚合网关，以**内网个人自托管**为主，也可以开启独立的公网端口做**小规模 Key 分发**。参考 new-api 的核心思想，保留渠道管理、协议转换、选路重试和请求观测；分发支持管理员直接发 Key（分组、倍率点数、额度与限流），也可以在公网端口开放一个仿 new-api 的精简用户门户，让用户自助注册、建 Key、签到领额度。不引入 Redis。

## ✨ 特性

- **渠道聚合**：支持 OpenAI Chat、OpenAI Responses、Anthropic、Vertex、Gemini（AI Studio）五类渠道；支持模型别名映射、优先级与权重。
- **三类调用入口**：OpenAI Chat Completions、Anthropic Messages、OpenAI Responses；同协议优先直通，跨协议通过内部中间表示（IR）转换，支持非流式与 SSE。
- **选路与故障转移**：同渠道重试、跨渠道降级、空回复检测、按状态码自动停用渠道，以及全局 HTTP 代理和内置 mihomo 代理池（渠道可按关键词绑定节点、失败换节点重发）。
- **请求预处理**：提示词正则、工具黑名单、thinking 清理、参数修改；提供可视化规则编辑和预览，以及限定链路的伪思考与历史续接。高级模式的正则包可按客户端 UA 启用，支持类酒馆宏模板、EJS 与脚本。
- **流量优化**：上游请求体压缩（zstd / br / gzip，可按渠道指定，被拒时自动明文重发）与管理端 / 门户的响应压缩、静态资源预压缩和长缓存。
- **统计与请求日志**：请求量、成功率、Token、平均延迟概览；可对照原始与改写后请求，查看网关响应及上游原始 JSON / SSE / 错误体。
- **小规模分发**：可选的公网端口开放 `/v1`（必须携带 Key）和用户门户；仿 new-api 的分组管理隔离私人渠道（分组勾选渠道与模型、带分组倍率），按模型倍率折算点数，支持总额度、每日额度、RPM 与并发限制，每个 Key 可单独决定是否记录正文。
- **用户门户**：公网端口上的自助页面，用户名 + 密码注册登录，自建 / 删除 Key、查看余额与调用记录、每日签到领额度；仿 new-api 模型广场的模型列表页可按分组、供应商与计费类型筛选并查看缓存读写价格；可用性页按 10 分钟一格展示各模型最近 6 小时的健康度与错误率，无人调用的模型自动测活；控制台右上角的通知中心常驻展示通知与公告。界面仿 new-api 用户侧，额度按可配置比例显示为美元。
- **轻量部署**：Node.js + SQLite 本地持久化，日志正文切块去重，冷数据整包压缩；React WebUI 提供渠道、分组、令牌、用户、通知、统计、请求日志、预处理、正则包、代理池、设置十一个页面。

## 快速开始

### 环境要求

- **Node.js ≥ 20.18.1，推荐使用较新的 Node.js 22**。当前 `undici` 依赖要求 Node.js ≥ 20.18.1。
- npm，在项目根目录安装依赖；无需额外数据库服务、Docker 或 Redis。
- `better-sqlite3` 包含原生模块；安装时优先使用预编译二进制，无法取得匹配版本时需要本机编译环境。

```bash
npm install

# 开发模式：前端热更新 + 后端监听源码变化
npm run dev
# WebUI：http://localhost:5173
# 用户门户：http://localhost:5174（需要以 AGGHUB_PUBLIC_PORT=3211 启动后端）
# 网关 API：http://localhost:3210

# 生产模式：先构建前端，再由后端单进程托管
npm run build
npm start
# WebUI 和网关 API：http://localhost:3210
```

- `npm run build` 依次构建管理端和用户门户，分别输出到 `web/dist/` 和 `portal/dist/`；后端通过 `tsx` 直接运行 TypeScript，**启动环境也需要安装开发依赖**，不要使用 `npm install --omit=dev`。
- 开发服务器将 `/api`、`/v1` 代理到 `localhost:3210`，门户的开发服务器代理到公网端口 `localhost:3211`。修改端口时，也要同步调整 [web/vite.config.ts](web/vite.config.ts) 和 [portal/vite.config.ts](portal/vite.config.ts) 中的代理目标。
- 可通过 `GET /api/health` 检查服务是否启动；该接口不要求访问令牌。

## 客户端接入

1. 打开 WebUI，在**渠道**页新增渠道，填写类型、上游地址、凭证和支持的模型，并按需设置模型映射、优先级与权重。
2. 在客户端（如 SillyTavern 或其他 LLM 工具）中选择入口格式，填写网关地址和模型名。
3. 内网端口默认无需 API Key；若客户端强制要求填写，可使用占位值。设置管理令牌后，客户端必须填写管理令牌或某个分发 Key。

| 入口 | 请求接口 | 常见客户端 Base URL |
| --- | --- | --- |
| OpenAI Chat | `POST /v1/chat/completions` | `http://<内网IP>:3210/v1` |
| OpenAI Responses | `POST /v1/responses` | `http://<内网IP>:3210/v1` |
| Anthropic Messages | `POST /v1/messages` | `http://<内网IP>:3210` |
| 模型列表 | `GET /v1/models` | 返回启用渠道配置的模型名（设了专属名的显示专属名）及映射别名并集 |

客户端对 Base URL 的拼接方式可能不同，请以最终请求路径为准。模型列表来自本地渠道配置，不会在每次请求时实时拉取上游列表。

配置管理令牌后，内网的 `/api` 管理接口与 `/v1` 匿名调用共用这个令牌，支持 `Authorization: Bearer <令牌>` 或 `x-api-key: <令牌>`。WebUI 会提示输入令牌，并保存在当前浏览器的 `localStorage` 中。

内网 `/v1` 的鉴权顺序：

1. 令牌命中某个分发 Key：按该 Key 的分组、模型白名单、额度和限流处理；Key 停用或过期时直接拒绝。
2. 没有设置管理令牌，或令牌等于管理令牌：作为 owner 调用，不受任何限制（和旧版本行为一致）。
3. 其余情况返回 `401`。

公网端口只接受分发 Key，管理令牌在公网端口无效，见下文[公网分发](#公网分发)。

## 渠道管理

### 上游类型

| 类型 | 上游协议 | 凭证与说明 |
| --- | --- | --- |
| OpenAI Chat（`openai`） | Chat Completions | Bearer API Key，可配置兼容服务的 Base URL |
| OpenAI Responses（`responses`） | Responses | Bearer API Key，可配置兼容服务的 Base URL |
| Anthropic（`anthropic`） | Messages | `x-api-key`，可配置兼容服务的 Base URL |
| Vertex（`vertex`） | Gemini 或 Vertex Claude | API Key / 服务账号 JSON，支持区域与 Base URL 配置 |
| Gemini（`gemini`） | Gemini API（Google AI Studio） | `x-goog-api-key`，可配置兼容服务的 Base URL |

Gemini（AI Studio）渠道与 Vertex Gemini 共用同一套 `generateContent` 转换（参数映射、`thinkingConfig`、`thoughtSignature` 往返、Schema 清洗完全一致），只是请求地址与鉴权不同：

- 请求 `{Base URL}/v1beta/models/{模型}:generateContent`，流式为 `:streamGenerateContent?alt=sse`；Base URL 默认 `https://generativelanguage.googleapis.com`，已以 `/v1`、`/v1beta`、`/v1alpha` 结尾时不再补版本段。模型名带 `models/` 前缀时自动去掉。
- 支持多 key 模式；不支持完整地址模式。
- “测试连接”和“拉取模型”分页读取 `GET /v1beta/models`，只保留 `supportedGenerationMethods` 含 `generateContent` 的模型，并去掉 `models/` 前缀。

Vertex 的区域默认 `global`：

- Gemini 使用 `generateContent` / `streamGenerateContent`；支持 API Key 或服务账号 JSON。
- 映射后的上游模型名以小写 `claude` 开头时，使用 Anthropic `rawPredict` / `streamRawPredict`。Vertex Claude 必须使用包含 `project_id`、`private_key`、`client_email` 的服务账号 JSON（API Key 仅支持 Gemini），由网关换取 OAuth 令牌；模型可用性取决于项目、区域及上游权限。
- 服务账号 JSON 填入同一个凭证输入框；当前没有 ADC / Workload Identity 接入。
- Vertex 跨格式转换使用模型别名时，应保持入口模型名与上游模型名的 `claude` 前缀分类一致，避免响应解析选择到另一种协议。

### 可配置项与连接测试

- 模型列表、`别名=上游模型` 映射、优先级、权重，以及启用 / 手动停用状态。
- 模型专属名：给模型列表中的某个模型换一个本渠道专用的名字，之后只有专属名会路由到该渠道，原名的请求不再分配过来（其他渠道不受影响）。适合把不稳定的渠道单独隔离，需要时再用专属名调用。
- 渠道级超时覆盖、User-Agent 覆写、去除非必要请求头。
- 一律重试：开启后，该渠道上游返回的任何 HTTP 错误（包括 `401`、`403`）都按瞬时错误在本渠道重试，次数跟随全局「单渠道重试次数」，用完才换渠道；同时本渠道命中熔断状态码时不再自动停用，多 key 模式下也不熔断 key（`429` / `402` 冷却照常）。用于兼容把限流返回成 `403` 的上游。代价是凭证真正失效时也不会被自动停用，每次请求都会先耗尽本渠道的重试次数。
- 假流式：开启后，客户端以流式请求该渠道时，网关改用非流式请求上游；等待期间每 20 秒向客户端发送一个 SSE 注释空帧（`: keepalive`）防止客户端或反代超时，拿到完整响应后按入口协议（Chat / Messages / Responses）合成标准 SSE 事件一次性下发。适合流式不稳定或不支持流式的上游。首个空帧会提前提交 `200` 响应头，之后的失败只能以 SSE 错误事件返回（仍可重试与换渠道）；渠道超时此时即等待完整响应的时长。
- 默认每个渠道保存一份凭证；OpenAI / Responses / Anthropic / Gemini 渠道可以开启「多 key 模式」，在同一渠道内轮询或并发使用多个 key（见下节）。当前没有并发配额或任意自定义请求头编辑器。
- Base URL 默认会自动补 `/v1` 和接口路径（`/chat/completions`、`/messages`、`/responses`）。OpenAI / Responses / Anthropic 渠道可以开启「完整地址」，Base URL 原样作为请求地址，兼容路径不标准的上游（如 `…/api/paas/v4/chat/completions`）；此时可另填「模型列表地址」，留空则把结尾的接口路径换成 `/models`。
- OpenAI / Responses / Anthropic 的“测试连接”和“拉取模型”使用上游 `GET /v1/models`（完整地址模式用模型列表地址），返回的模型列表原样读取，不截断。因此测试结果不能完全代表实际生成接口的可用性。
- Vertex 的测试会发送一次输出上限为 1 Token 的生成请求，可能产生实际调用费用，不返回可拉取的模型列表。

### 多 key 模式

开启后 API Key 改为每行一个（自动去除空行和重复项），在两种互斥的子模式中选一种。Vertex 渠道不提供该模式。

- **多 key 轮询**：每次请求先用排在最前的可用 key。key 失效时熔断它并立即换下一个，换 key 不消耗同渠道重试次数，也不等待重试间隔。「连续限流次数」（默认 `1`）大于 1 时，同一个 key 的 `429` / `402` 要连续达到该次数才冷却并换 key；未达到时等待全局「重试间隔」后用同一个 key 重试，同样不消耗同渠道重试次数。
- **多 key 并发**：每次请求按轮转顺序取「并发 key 数」个可用 key，同时请求上游。流式请求里最先产出有效内容（正文、思考或工具调用）的那一路胜出；非流式请求里最先完整返回且通过校验的那一路胜出。其余请求立即中断，不记日志、不熔断。还没决出胜者时失败的那一路不补位；整组都失败才算一次尝试失败，之后按同渠道重试次数再取一组，次数或 key 用完后换渠道。注意上游实际被调用 N 次，落选的请求也可能已经产生费用；计费只按胜出那一路的用量。
  - **单 key 竞速**：并发模式下的开关。开启后每次请求只用排在最前的可用 key，同时向上游发起「并发请求数」路请求，胜出规则与上面相同；key 列表只填一个 key 也能竞速。同一组里有一路胜出时，其余几路的失败不熔断也不冷却该 key；整组失败时该 key 只计一次失败。该 key 熔断或冷却后，下一组改用后面的可用 key。

key 失效的判定与恢复：

- 命中全局「熔断状态码」（默认 `401,403`）：按全局「连续失败次数」累计，达到后熔断该 key。熔断时长跟随全局「自动恢复」分钟数，为 `0` 时只能手动恢复。熔断过的 key 恢复后，在成功之前再命中一次就立即熔断。
- `429` 和 `402`：冷却，时长优先取上游的 `Retry-After`，否则用渠道的「限流冷却（秒）」（默认 `300`）。并发模式下首次命中就冷却；轮询模式按「连续限流次数」累计，计数跨请求保留在内存里，该 key 成功一次即清零，冷却到期后重新累计。
- `5xx`、超时、网络错误不熔断 key，按普通重试处理。
- 多 key 模式下 key 级熔断不受「自动熔断」总开关影响（渠道开启「一律重试」时除外，见上节），也不计入渠道级的自动停用。key 全部熔断时渠道状态不变，选路时自动跳过；有 key 到期恢复后渠道自动回到候选。
- 熔断状态按 key 指纹存进数据库，重启后保留，调整 key 顺序或增删其他 key 不受影响。编辑弹窗里能看到每个 key 的状态，可以逐个或全部重置；渠道卡片显示可用 key 数，日志详情显示本次使用的上游 key（序号 + 脱敏值）。
- 测试连接与拉取模型使用第一个 key。

### 上游请求体压缩

Agent 类客户端的输入远大于输出，发往上游的请求体是流量的绝对大头。开启后，AggHub 只压缩**自己发往上游**的请求体，不改变客户端的请求和上游的响应；压缩使用异步 zlib API，在线程池中执行，不占主线程。总开关默认关闭，关闭时行为与未启用前一致，只是日志会多记录明文字节数，便于对比。

| 设置项 | 默认 | 说明 |
| --- | --- | --- |
| 启用压缩 | 关闭 | 总开关；关闭时所有渠道都发明文 |
| 默认算法 | `zstd` | 渠道设为「跟随全局」时使用的算法 |
| zstd 级别 | `2` | `1`～`19` |
| zstd 窗口 | `23` | 下拉选择 `0` 或 `10`～`23`；`0` = 级别默认，`23` = 8 MB，旁边显示换算大小 |
| br 质量 | `2` | `0`～`11` |
| gzip 级别 | `1` | `1`～`9` |
| 最小压缩体积 | `4 KB` | 请求体小于该值不压缩，`0` = 全部压缩 |
| 自动回退 | 开启 | 判定为压缩被拒时在同一次尝试内明文重发 |
| 回退状态码 | `400,415` | 逗号分隔 |
| 匹配正则 | 见下 | 不区分大小写，只匹配错误体前 2000 字符；留空只看状态码 |
| 记忆时长 | `360` 分钟 | 明文重发成功后在该时段内对该渠道发明文；`0` = 直到重启 |

手机（如红米 Note 4X、Cortex-A53）推荐 zstd 2 + 窗口 23、gzip 1、br 2。zstd 需要 Node ≥ 22.15，设置页会显示当前 Node 版本与 zstd 是否可用；运行时不支持时，选择 zstd 的渠道直接按不压缩处理。

默认的匹配正则为：

```text
json|pars|decod|encod|compress|gzip|zstd|brotli|invalid character|unexpected token|unsupported (media|content|encoding)
```

设计意图是只在错误体看起来与编码、解析或压缩有关时才重发，「prompt is too long」「Unsupported parameter」这类真实的 `400` 不会触发把大请求体再明文传一遍。

上游兼容性如下，实际以渠道里的「压缩测试」结果为准：

| 上游 | 支持 |
| --- | --- |
| OpenAI 官方 `/v1/responses` | zstd（官方文档明确） |
| Anthropic 官方 | gzip（社区实测，非官方文档） |
| new-api 系 | gzip、br；zstd 自 rc.23（PR #6545）起 |
| one-api | gzip |

**回退与记忆。** 状态码命中回退列表、且错误体匹配正则时（两者同时命中），才判定为压缩被拒。开启自动回退后，网关在**同一次上游尝试内**改用明文重发，不占用同渠道 / 跨渠道重试次数，超时仍受该次尝试约束；只有明文重发成功才把「该渠道 × 该算法不支持」写进内存记忆。记忆期内该组合直接发明文，不再先压缩一次；记忆不落库，重启后清空，保存或删除渠道、或在渠道弹窗里点「清除」也会重置。渠道卡片上有「压缩回退」徽标，编辑弹窗里会显示已判定不支持的算法和剩余时间。

**渠道里的压缩测试。** 编辑渠道时可选择测试模型并点「压缩测试」，它会依次发送明文基线 + gzip + br + zstd 四个最小请求，级别和窗口取当前全局设置，不受最小体积和「不支持」记忆影响，也不会修改记忆。测试会实际调用上游，约消耗几十 token。结论含义：`✅ 支持`（上游 2xx）、`❌ 拒绝`（命中回退状态码与正则）、`⚠️ 其他错误`（其他失败）、`跳过`（基线失败或当前 Node 不支持 zstd）。

**日志字段。** 请求详情会记录这次发往上游的压缩明细：

| 字段 | 含义 |
| --- | --- |
| `upstream_encoding` | 压缩算法与参数，如 `zstd-2 w23`、`gzip-1`；未压缩为空 |
| `upstream_raw_bytes` | 发往上游的明文字节数；总开关关闭时也会记录 |
| `upstream_sent_bytes` | 实际发出的字节数；发生回退时是压缩与明文两次发送之和 |
| `compress_ms` | 压缩耗时（含线程池排队），毫秒 |
| `compress_status` | 压缩结果，取值见下表 |
| `compress_note` | 被拒时的上游错误摘要，或压缩异常信息（≤300 字） |

| `compress_status` | 含义 |
| --- | --- |
| `compressed` | 已压缩发送 |
| `fallback_ok` | 压缩被拒，明文重发成功 |
| `fallback_failed` | 压缩被拒，明文重发仍失败（不写入记忆） |
| `rejected` | 压缩被拒，但回退开关关闭 |
| `off` | 渠道关闭压缩 |
| `below_min` | 请求体小于阈值 |
| `channel_unsupported` | 记忆期内该渠道 × 算法被判定不支持 |
| `runtime_unsupported` | 当前 Node 不支持该算法（zstd 需 Node ≥ 22.15） |
| `compress_error` | 压缩本身出错，改发明文 |

日志详情里显示为 `上游压缩：zstd-2 w23 · 612.3 KB → 118.4 KB（19.3%）· 3.2ms · 已压缩`，括号内是实际发送字节占明文的比例；总开关关闭时显示为 `上游请求体 612.3 KB（未启用压缩）`。

建议的上线步骤：

1. `node -v` 确认 ≥ 22.15，然后 `npm install`、`npm run build`。
2. 可选：在分发机上跑基准脚本，确认 zstd-2 / gzip-1 的实际耗时。
3. 在设置页确认级别为手机推荐值：zstd 2 + 窗口 23、gzip 1、br 2。
4. **先不开总开关**，逐个渠道点「压缩测试」：zstd 通过的保持「跟随全局」；只支持 gzip 或 br 的单独指定算法；都不支持的设为「关闭」。
5. 打开总开关，观察日志详情；可用下面的 SQL 汇总：

```sql
SELECT compress_status, upstream_encoding, COUNT(*) AS n,
       SUM(upstream_raw_bytes) AS raw, SUM(upstream_sent_bytes) AS sent,
       ROUND(100.0 * SUM(upstream_sent_bytes) / SUM(upstream_raw_bytes), 1) AS pct,
       ROUND(AVG(compress_ms), 2) AS avg_ms
FROM request_logs
WHERE created_at >= (strftime('%s','now') - 86400) * 1000
GROUP BY 1, 2 ORDER BY n DESC;
```

6. 出现 `fallback_ok` 说明渠道不支持当前算法，改算法或设为「关闭」，再点「清除」重置记忆。

### 代理池

侧栏的**代理池**页管理一个由网关托管的 [mihomo](https://github.com/MetaCubeX/mihomo) 进程，让渠道请求经池内节点发出：

- **内核**：默认使用 `data/mihomo/mihomo(.exe)`，可在页面上从 MetaCubeX/mihomo 的 GitHub Releases 下载最新版本，也可以在设置里指定自有内核路径。总开关开启后随网关自启，配置变更时热重载。
- **节点来源**：订阅链接（base64、Clash YAML、SIP008、逐行 URI）或手动粘贴节点 URI；同一节点按身份去重。可设置入口代理（节点 URI 或 http(s) / socks5 地址）作为所有节点的前置跳板，以及下载内核 / 拉取订阅专用的代理。
- **测速与拨测**：支持批量测速和定时拨测，连续失败达到阈值的节点自动禁用。
- **渠道绑定**：渠道开启「启用代理池」后，可用包含 / 排除关键词筛选节点。上游返回 `429` / `403` 或发生网络错误时，节点进入冷却并在本次尝试内换节点重发，换节点不消耗渠道重试次数；池内没有可用节点时按换渠道处理。渠道测试与压缩测试同样走池内节点。
- 请求日志记录本次使用的代理节点，支持按节点名搜索。
- 代理池设置以 JSON 形式保存在设置项 `proxy_pool` 中；mihomo 控制器默认监听 `19090`，节点入站端口从 `19100` 起递增分配，控制器密钥首次启动时随机生成。

## 选路、重试与超时

1. 根据请求模型筛选启用渠道：设了专属名的模型只认专属名并换回原名，模型映射用于将对外别名替换为上游模型名。
2. `priority` 越大越优先；同一优先级内按 `weight` 加权随机。
3. 当前渠道失败后先按配置进行同渠道重试；仍失败则排除该渠道，选择剩余候选，同级耗尽后降到较低优先级。
4. 开启自动熔断时，渠道连续命中配置的状态码达到「连续失败次数」（默认 `1`）后标记为自动停用（开启「一律重试」的渠道不参与）：成功会清零计数，其他错误不影响计数。「自动恢复」大于 0 时，到期后由每分钟的维护任务恢复启用；恢复后的渠道处于半开状态，再命中一次就立即停用。自动恢复为 `0`（默认）时需要在渠道页手动恢复。计数保存在内存中，重启后清零。

两个重试设置都表示**首次尝试以外的额外次数**：默认同渠道重试 `1` 次、跨渠道重试 `2` 次，即候选充足时最多尝试 3 个渠道、每个渠道最多 2 次。实际次数还受错误类型、熔断及客户端断开影响。

- 网络异常、超时、`429`、`5xx` 等瞬时错误会优先在同渠道重试；`400`、`413`、`422` 直接结束请求，不切换渠道。其他错误可能跳过本渠道剩余重试。
- 渠道开启「一律重试」后，上游任何 HTTP 错误都在本渠道重试；本地参数错误、上游 `2xx` 之后的处理失败和客户端取消仍按原规则处理。
- 非流式请求上游已经返回 `2xx` 之后的处理失败（响应体超出缓冲上限、不是合法 JSON、空回复、协议转换失败）不再重试，也不换渠道，直接把错误返回客户端；这些判定之前会先解析 usage，按实际用量计费。
- 权重 `0` 不能用于保证停用：当同层剩余候选权重全为 `0` 时仍可能被选中。需要停用时请关闭渠道启用开关。

**流式与超时边界：**

- 流式初始事件会先缓冲，尚未向客户端输出实质内容时，错误或空回复可以进入重试；一旦开始输出，就不会再重试或切换渠道。
- 流式保活：超过 `stream_keepalive_ms`（默认 `30000`，`0` 关闭）没有向客户端输出任何数据时，补发一行 SSE 注释 `: keepalive`，避免 Cloudflare 隧道等反代在等待首字或重试期间因长时间无数据断开。首次保活会提前提交 `200` 响应头，之后仍可重试与换渠道；若最终失败，错误改为按入口格式写出的 SSE 错误事件，不再是 HTTP 错误状态码（日志照常记录真实状态码）。非流式请求不做保活。
- 一次请求里所有真正发往上游的尝试（重试、换渠道）的 usage 会累加计费；多 key 并发竞速中落选的尝试仍不计费。流式请求已发往上游但还没有任何输出时（例如客户端在首个输出前断开），至少按输入估算计费，按次费用仍只在产生输出时计入。
- 全局超时默认 `120000 ms`，可被渠道配置覆盖。非流式用于约束单次上游请求及响应读取；流式每收到一个带数据的 SSE 事件会重置计时，主要约束事件间的空闲时间。
- 每次重试独立计时，重试间隔另算；Vertex OAuth 等前置操作也有独立行为，因此该值不能视为整个客户端请求的总耗时上限。
- 全局 `proxy_url` 使用 HTTP 代理，作用于上游请求；当前没有每渠道代理配置。

## 公网分发

### 双端口

| 端口 | 默认监听地址 | 提供的接口 | 鉴权 |
| --- | --- | --- | --- |
| 内网 `PORT`（默认 `3210`） | 所有网卡，可用 `HOST` 修改 | WebUI、`/api`、`/v1` | 管理令牌可选；带分发 Key 时按 Key 限制 |
| 公网 `AGGHUB_PUBLIC_PORT` | `127.0.0.1`，可用 `AGGHUB_PUBLIC_HOST` 修改 | `/v1`、用户门户（页面与 `/api/user`） | `/v1` 必须携带 Key；门户用登录 Cookie |

两个端口在同一个进程里，共享数据库、渠道、设置和限流计数。`AGGHUB_PUBLIC_PORT` 未设置时只启动内网端口，行为与旧版本一致。公网端口默认只监听回环地址，由 cloudflared、frp、nginx、Caddy 等暴露到公网；管理界面始终只在内网端口上。

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `PORT` | `3210` | 内网端口 |
| `HOST` | 不设（所有网卡） | 内网监听地址；VPS 部署可设为 `127.0.0.1`，再通过 SSH 隧道访问管理界面 |
| `AGGHUB_PUBLIC_PORT` | 不设 | 设置后开启公网端口，不能与 `PORT` 相同 |
| `AGGHUB_PUBLIC_HOST` | `127.0.0.1` | 公网端口监听地址 |
| `AGGHUB_TRUST_PROXY` | `loopback` | 公网端口的 Express `trust proxy`，决定是否从 `X-Forwarded-For` 取客户端 IP；直接暴露端口时设为 `false` |

运行模式放在环境变量里，WebUI 无法修改，管理令牌泄露也改变不了安全边界。

### 分组

侧栏的**分组**页仿 new-api 管理分组，每个分组包含：

- **名称与描述**：名称是唯一标识，Key 和用户按名称引用；改名时会同步更新所有引用。描述显示在门户的分组选择里。
- **分组倍率**：扣费点数 = 模型定价算出的点数 × 分组倍率（例如 vip `0.8`、svip `1.5`），向上取整。
- **允许的渠道与模型**：逐个勾选。只有同时勾选的「渠道 × 模型」组合才能被本组的 Key 调用；模型选项为已勾选渠道对外的模型名（含专属名和重映射别名）。之后新增的渠道或模型需要回到分组页勾选。
- **公开**：公开分组所有门户用户都能选；非公开分组需要在**用户**页分配给指定用户。
- **排序**：越小越靠前，也是门户里的显示顺序。

删除分组会把它从所有用户和 Key 上移除，失去分组的 Key 无法调用，需要重新选择分组；删除渠道会自动从各分组里去掉。内网匿名（owner）调用不受分组限制。

从旧版本升级时，原来写在渠道上的分组会自动转成分组定义：渠道为原来属于该分组的渠道，模型为这些渠道当时的全部模型，倍率为 1；原「门户可用分组」设置转为公开分组，门户用户已有的 Key 归入第一个公开分组。迁移后的权限与升级前一致。

### 分发 Key

- 在**令牌**页创建 Key，格式为 `sk-agh-` 加 40 位字母数字，明文保存，可随时复制或重新生成。令牌页只列管理员创建的 Key，门户用户自建的 Key 在**用户**页展开查看。
- 每个 Key 可设置：可用分组（至少一个）、模型白名单（支持 `*`，留空不限）、RPM、并发上限、总额度、每日额度、过期时间、正文记录（跟随全局 / 记录 / 不记录）和备注。
- 管理员发的 Key 可以属于多个分组，可用的渠道 × 模型取各分组的并集；同一组合被多个分组允许时，按倍率最低的分组计费。请求日志记录本次计费所用的分组。
- 建议建一个公开的 `public` 分组给分发用；自己在外面使用时，单独建一个勾选全部渠道和模型、倍率为 1 的分组，再建一个只属于它、不设额度的 Key。
- Key 无权使用的模型返回与「没有渠道支持该模型」相同的错误，不暴露私人渠道里有哪些模型；`/v1/models` 只列出该 Key 可用、且已配置倍率的模型。
- 同一个 Key 在内网和公网端口都能使用，额度和限流共享。

### 模型定价与额度

```text
未缓存输入 = max(0, 输入 − 缓存读取 − 缓存写入)
费用 = (未缓存输入 × 输入价 + 缓存读取 × 缓存读价 + 缓存写入 × 缓存写价 + 输出 × 输出价) ÷ 1M
     + 按次价
```

- 最终扣费还要乘上本次命中分组的倍率，见[分组](#分组)。
- 定价在令牌页的「模型定价」卡片里按「金额 / 1M Token」和「金额 / 次」编辑，可以试算。按客户端请求的模型名（映射前）匹配：精确名优先，其次是非通配部分最长的 `*` 通配符，长度相同按列表顺序。
- 「导入模型定价」列出渠道里没有定价、或者只命中通配规则的模型（含重映射别名与专属名），可以从 OpenRouter 公开价格自动匹配（走设置里的 HTTP 代理），核对后批量生成规则。
- 没有命中任何定价的模型，Key 调用返回 `403`。默认定价表带一条 `*`（每百万 Token $2），删除后只有已定价的模型能被 Key 调用。
- 按次价格只在产生输出时计入。
- 内部仍按整数点数记账（`1 = 500000` 点，与 new-api 一致），定价保存为每 Token 点数倍率；管理端与门户统一换算成金额显示，余额符号可在设置页修改（只改变显示，不做汇率换算）。
- 上游没有返回 usage 时（例如流式请求被客户端中途断开），按「中日韩字符 1 个算 1 Token、其他字符 4 个算 1 Token」估算，只用于计费，日志里的 Token 列仍记录上游原值。
- 请求开始时检查总额度和今日额度，请求结束时扣费。带 Key 的调用在首次请求上游之前会按「输入估算 + 声明的输出上限」预扣额度：输出上限取请求里的 `max_tokens` / `max_completion_tokens`，未声明按 `4096`，再乘候选分组中的最大倍率；可用额度（门户用户余额，或管理员 Key 的 `quota_total` 减已用）不足以支付预扣时返回 `429`，提示调小 `max_tokens` 后重试，结算后释放。预扣是进程内的，重启清零；管理员 Key 的 `quota_total` 留空（不限）时不受预扣限制，预扣也不受「公网 Key 强制 `max_tokens` 上限」这类参数规则影响（按请求体里声明的值计算）。每日额度仍只在准入时检查一次，最后一次请求和并发请求可能透支少量额度，门户并发上限（新库默认 `2`，见[配置与默认值](#配置与默认值)）可以限制透支的范围。
- 每日额度按服务器本地日期重置。用量记录在独立的 `usage_daily` 表里，请求日志过期清理不影响额度和用量历史。
- owner 请求也会计算费用并写入日志，方便查看自己的用量，但不扣费。

### 限流与错误响应

- RPM（滑动 60 秒窗口）和并发上限按 Key 计算，门户用户名下的所有 Key 共用一份；只对三个生成接口生效，计数在内存里，重启后清零。额度预检与限流放行时会给这次调用写入准入标记，中继遇到带 Key 却没有该标记的调用直接返回 `429`，以后新增入口也不会绕过准入。
- 两个端口都拒绝路径中含 `//` 的请求（返回 `404`），避免绕过按路径的准入与鉴权。
- 公网端口上同一 IP 在 5 分钟内鉴权失败 10 次，会被封禁 15 分钟；只统计鉴权失败的请求，带有效 Key 的调用不受 IP 封禁影响，IPv6 按 `/64` 归并计数。
- 这些在进入中继之前被拒绝的请求不写请求日志。

| 情况 | 状态码 | OpenAI 格式 `type` | Anthropic 格式 `type` |
| --- | --- | --- | --- |
| Key 无效 | `401` | `invalid_api_key` | `authentication_error` |
| Key 停用 / 过期 | `403` | `key_disabled` / `key_expired` | `permission_error` |
| 门户用户被停用 | `403` | `user_disabled` | `permission_error` |
| 总额度 / 今日额度用完、门户用户余额不足 | `429` | `insufficient_quota` | `rate_limit_error` |
| RPM / 并发超限、鉴权失败过多 | `429`，带 `Retry-After` | `rate_limit_exceeded` | `rate_limit_error` |

### 公网端口的安全措施

- 先鉴权、后解析请求体，未鉴权的请求不会触发 JSON 解析。
- **SSRF 防护**：Gemini 上游需要下载远程图片时，拒绝回环、私有网段、链路本地（含云元数据地址 `169.254.169.254`）、CGNAT、组播、保留地址和 IPv6 ULA 等；建立连接时再次校验解析结果，防止 DNS 重绑定；重定向改为手动跟随，最多 3 次并逐跳检查。配置了全局 HTTP 代理时，域名由代理解析，只能做本地预检查。
- **远程图片限额**：只对 Gemini 上游的远程图片 URL 生效，流式读取并按解压后的字节数封顶（单张沿用设置里的单张上限），单次请求最多下载 16 张、解压后总量 64 MiB、最多 4 张并发；响应 `Content-Type` 必须是 `image/*`，请求头带 `accept-encoding: identity`。
- **错误脱敏**：返回给公网客户端的上游错误会先截断到 2000 字符，再把 URL、IP 和疑似密钥替换为占位符，网络错误统一显示「上游连接失败」；直通流式中的上游错误事件不原样转发。请求日志保留原文，但入库的 `error_message` 同样截断到 2000 字符。开启「脱敏上游报错信息」后，上游与网络错误只返回 HTTP 状态码和标准短语（如 `503 Service Unavailable`），「排除的状态码」（默认 `400`）照常返回脱敏后的原文；网关自身判定的错误（无可用渠道、余额不足等）不受影响。错误信息被改写的日志在列表中标「已改写」，详情里点「显示原始请求」可查看上游原文。`model` 名称超过 256 字符的请求直接返回 `400`，错误信息不回显模型名。
- 关闭 `X-Powered-By`；`/v1` 返回 `Access-Control-Allow-Origin: *`，方便浏览器端客户端调用（鉴权走请求头，不使用 Cookie）。

### 反向代理与客户端 IP

`AGGHUB_TRUST_PROXY` 默认为 `loopback`，即信任从回环地址连入的代理所设置的 `X-Forwarded-For`。cloudflared、nginx、Caddy 都会设置这个头；frp 的普通 TCP 隧道、netsh portproxy、`ssh -R` 这类本机转发后面，服务端看到的来源都是 `127.0.0.1`：默认的 `loopback` 会信任本机发来的 `X-Forwarded-For`，客户端可以伪造这个头绕过按 IP 的限速与封禁，因此这类部署应设 `AGGHUB_TRUST_PROXY=false`；代价是所有人共用 `127.0.0.1` 这一个计数，一人连续失败可能让全站在一段时间内无法登录（带有效 Key 的 API 调用不受影响）。最好改用能传递真实 IP 的反向代理（HTTP 模式的 frp、nginx、Caddy 等）并正确设置 `AGGHUB_TRUST_PROXY`。客户端 IP 记录在请求日志中。

Caddy 示例：

```text
api.example.com {
	reverse_proxy 127.0.0.1:3211
}
```

nginx 示例（网关已经发送 `X-Accel-Buffering: no`，SSE 不会被缓冲）：

```nginx
location / {
    proxy_pass http://127.0.0.1:3211;
    proxy_http_version 1.1;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_read_timeout 3600s;
}
```

### 响应压缩与静态缓存

设置页「响应压缩与静态缓存」卡片：

| 设置项 | 默认 | 说明 |
| --- | --- | --- |
| 响应压缩 | 开启 | 管理端 / 门户的接口 JSON 与页面资源 |
| gzip 级别 | `6` | `1`～`9` |
| br 质量 | `0` | `0` = 不用 br，只用 gzip；`1`～`11` |
| 压缩阈值 | `1024` 字节 | 响应小于该值不压缩，`0` = 全部压缩 |
| 静态资源缓存（天） | `365` | `/assets` 下的文件按 immutable 缓存；`0` = 保持默认 |
| 预压缩文件 | 开启 | 存在 `.br` / `.gz` 时直接返回 |

`/v1` 与 SSE 流式响应永远不压缩；显示 Key 明文的接口 `/api/user/keys/:id/key` 也不压缩，避免 BREACH 侧信道。br 质量为 `0` 时只协商 gzip，CPU 开销更可预期。

构建时 Vite 插件 `scripts/vite-precompress.mjs` 会遍历 `web/dist/assets` 与 `portal/dist/assets`，为 ≥1 KB 的 `.js` / `.css` / `.svg` / `.json` / `.txt` / `.wasm` 生成 `.br` 和 `.gz` 副本。开启「预压缩文件」后，命中的请求直接返回预压缩文件，不占运行时 CPU；如果分发机是拷贝 `dist` 而不是自行构建，要连同 `.br` / `.gz` 一起拷贝。

`/assets` 下带哈希的文件会带 `Cache-Control: public, max-age=…, immutable`（天数可设，`0` = 不设置、保持 express 默认）；门户首页 HTML 仍是 `no-cache`，换版本后能及时拿到新的资源引用。

Cloudflare 缓存规则（只涉及后台配置）：

- Cache Rules：URI 路径**精确等于** `/api/user/background` 或 `/api/user/brand-icon` → Eligible for cache，Edge TTL 使用源站的 `Cache-Control`。这两个地址由源站设置 immutable，并带 `?v=时间戳`，换图后自然失效。
- **严禁**写成 `/api/user/*` 这类通配，否则 `/api/user/self`、`/api/user/keys` 等个人数据可能被缓存后发给其他用户。
- `/assets/*` 的 `.js` / `.css` 按扩展名本就在 Cloudflare 默认缓存范围内；有了 immutable 之后，命中边缘缓存时不再回源。

### 分发时的注意事项

- 预处理的三类规则可以按「调用来源」（内网匿名 / 内网 Key / 公网 Key / 门户用户 / 自动测活）和「指定 Key」限定作用范围。例如只对公网 Key 强制 `max_tokens` 上限，或删除 Responses 的 `tools`、强制 `store: false`。这类规则只改发往上游的请求，不影响额度预扣的口径（预扣按客户端请求体里声明的输出上限计算）。
- Responses 直通时的托管工具（`web_search` 等）和 `store` 由上游另外计费，点数覆盖不到，建议用上面的规则限制。
- 伪思考库和推理密文暂存的容量全站共享，分发用户请求多时会挤掉旧记录，必要时调大容量。
- 每个 Key 的正文记录开关只影响请求日志里的正文，模型、Token、点数、IP 等元数据始终记录；伪思考库和推理暂存属于续接功能数据，不受这个开关影响。

## 用户门户

公网端口开启后，同一个端口上的 `/` 就是用户门户（需要先 `npm run build`）。界面仿 new-api 普通用户侧：顶栏 + 可折叠侧边栏 + 内容面板，天蓝主色，只有浅色模式；可另配背景图（见[门户背景](#门户背景)），未设置时内容面板为白色。

| 页面 | 内容 |
| --- | --- |
| 登录 / 注册 | 用户名 + 密码；开启 Discord 登录后另有「使用 Discord 登录 / 注册」按钮；用户名 3～20 位字母、数字或下划线（不区分大小写），密码 8～128 个字符；注册后跳回登录页 |
| 概览 | 余额、今日消耗、历史消耗、请求次数及最近 7 天迷你图；签到月历；Base URL 接入信息与最新公告面板（最近 5 条，可查看全部） |
| 模型列表 | 仿 new-api 模型广场：按分组、供应商、计费类型筛选，搜索、排序与视图切换，价格按所选分组倍率显示，点击模型查看各分组明细 |
| 可用性 | 用户可用分组里每个模型最近 6 小时的健康度与错误率，每格 10 分钟，悬停查看该格的请求数、失败数与测活次数 |
| 令牌 | 创建（名称 + 分组 + 可选过期时间）、复制、启停、改分组、删除；每个 Key 显示分组、已用额度和最近使用时间；被管理员停用的 Key 开关禁用并显示「管理员已停用」 |
| 使用日志 | 按令牌、模型筛选，显示时间、模型、Token、花费、耗时和状态；错误信息经过脱敏 |
| 个人中心 | 账户统计、修改密码（Discord 注册的账号没有密码，不显示此项）、退出登录 |

### 模型列表

控制台侧栏的**控制台**组依次为概览、模型列表、可用性、令牌、使用日志，模型列表页仿 new-api 模型广场：

- 左侧筛选栏：分组（带 ×倍率）、供应商、计费类型（按量计费 / 按次计费 / 免费）。供应商按模型名推断（`claude` → Anthropic、`gpt` / `o` 系列 → OpenAI、`gemini` → Google、`deepseek`、`qwen` 等，其余归入「其他」）；窄屏下收起为「筛选」按钮，点开为抽屉。
- 搜索、排序（名称 / 输入价 / 输出价）、`/1M` 与 `/1K` 价格单位切换、卡片 / 表格视图切换，视图与单位记在浏览器本地。
- 卡片和表格都显示输入、输出、缓存读取、缓存写入与按次价格。选中某个分组时价格 = 基础价 × 该分组倍率；选「全部分组」时按该模型可用分组中最低的倍率显示。
- 点击模型打开右侧详情抽屉：基础价格、各分组价格表（分组 | 倍率 | 输入 | 输出 | 缓存读取 | 缓存写入 | 按次）与计费说明。
- 概览页原先「接入信息」下方的模型价格表已移到这里，概览页改为显示最新公告面板。数据接口为 `GET /api/user/pricing`，返回可用分组、模型基础价格及每个模型的可用分组，替换旧的 `GET /api/user/models?group=`。

### 可用性

可用性页（`/console/status`）登录后可见，列出用户可用分组（公开分组 + 分配给该用户的分组）里已定价的模型，按服务器时间对齐 10 分钟一格，共 36 格，最后一格是当前尚未结束的时段。

- **健康度**：每格按错误率判定，`≤ 10%` 正常、`10% ~ 50%` 波动、`> 50%` 故障，没有结果为无数据；「当前」取最近一个有结果的格子，右侧为 6 小时合计错误率与请求数。顶部四个状态卡片显示各状态的模型数，点击可按状态筛选；页面每分钟自动刷新。
- **统计范围**：只算最终结果（不含中间重试），且只算该用户分组里服务这个模型的渠道上的结果，同名模型在其他渠道（例如私人渠道）上的调用不计入；没走到任何渠道的失败（如「没有可用渠道」）也计入。熔断停用的渠道上的模型照常显示，手动停用的渠道不算。
- **不计入的失败**：客户端主动断开（`499`）、请求本身不合法（上游或本地的 `400` / `413` / `422`），以及没走到渠道就被拒绝的 4xx（余额不足、限流、未定价等）。测活结果不做这项排除，全部计入。
- **自动测活**：开启公网端口后，服务端每 30 秒检查一次，某个模型 10 分钟内没有计入的结果时，以「自动测活」来源走一遍完整中继（与真实请求相同的选路、重试与换渠道），请求为一条 `hi`、`max_tokens: 32` 的非流式 Chat Completions；当前格子只剩 1 分钟仍没有结果时也补测一次，避免间隔漂移跳过整格。测活只在分组允许的渠道里选路，同一模型在不同分组里由不同渠道服务时分开测；只测公开分组和已分配给启用用户的分组，同时最多 3 个并发。可在设置页「用户门户 → 可用性自动测活」关闭，关闭后只统计真实请求。
- 测活照常写入请求日志（来源为「自动测活」，可在管理端日志页按来源筛选，Key 为空），会消耗上游额度但不扣任何用户或 Key 的额度；预处理规则不限来源时同样作用于测活。数据接口为 `GET /api/user/availability`。

### 通知中心

控制台右上角的铃铛打开通知中心，带未读数角标，弹层分**通知**与**公告**两栏：

- 通知：一段 Markdown 常驻说明；内容有变化时，用户进入控制台会自动弹出一次。内容由设置项 `portal_notice` 提供。
- 公告：时间线（类型颜色点 + 内容 + 附加说明 + 发布时间），按发布时间倒序显示已发布的最近 20 条；`portal_announcements_enabled` 关闭时门户不显示公告。
- 已读状态只存在浏览器本地并按用户区分：通知按内容判断，公告按 id + 更新时间判断，公告被编辑后重新计为未读。
- 内容支持 Markdown 子集（标题、粗体、斜体、删除线、行内代码、代码块、链接、自动链接、列表、引用、分割线）；原始 HTML 按文本显示，链接只允许 http(s)、mailto 与站内路径。
- 公告接口为 `GET /api/user/notices`，返回通知与已发布公告。

### 门户背景

设置页「系统设置 → 门户背景」可为登录 / 注册页与控制台配置背景图：

- `portal_background` 留空不启用；可填 http(s) 图片链接，或上传后自动生成的 `/api/user/background?v=时间戳`。链接不允许包含引号、括号、反斜杠、尖括号与空白；门户走 HTTPS 时图片也应使用 https 链接。
- `portal_background_opacity`（`0`～`100`，默认 `80`）控制内容面板不透明度，`portal_background_blur`（`0`～`40`，默认 `12`）为毛玻璃模糊像素，`portal_background_dim`（`0`～`90`，默认 `10`）为背景图上叠加的白色遮罩浓度，保证直接压在图上的顶栏 / 侧栏文字可读。
- 上传接口为 `PUT /api/settings/background`，JSON `{ data: "data:image/...;base64,..." }`；支持 PNG / JPEG / GIF / WebP，解码后不超过 5 MB，与品牌图标一样存入 `site_assets` 表，上传后立即生效。`GET /api/user/background` 在内网端口与公网端口都免鉴权提供（管理端可预览），带版本号长期缓存。
- 上传前可在浏览器里转成 WebP：默认开启，质量默认 `85`，最大宽度默认 `1920`（`0` = 不缩放）；GIF 不转换，转换后不比原图小或浏览器不支持编码时上传原图。这三个选项只保存在当前浏览器（`localStorage`），不进服务端设置。
- 门户状态接口 `GET /api/user/status` 新增 `background`、`background_opacity`、`background_blur`、`background_dim` 字段。
- 启用后登录 / 注册页与控制台都铺满背景图，顶栏、侧栏透明（顶栏带模糊，内容滚到下面时不串字），内容面板与登录卡片为半透明毛玻璃，面板内卡片再叠一层更淡的白；下拉菜单、通知弹层、对话框、Toast 保持不透明，移动端侧栏抽屉同样不透明。未设置背景图时门户外观与原来完全一致。
- 服务端在门户首屏 HTML 中注入背景 CSS 变量（与标题、图标注入相同机制），首屏不会先闪白底。

### 额度与计费

- 用户余额以点数存储，管理端与门户都换算成金额显示；门户顶栏、登录注册页的名称与图标、网页标题都可以在设置页「品牌与金额显示」卡片修改，图标支持 emoji / 文字、图片链接或上传图片；门户背景图在「门户背景」卡片配置，见[门户背景](#门户背景)。
- 用户可用的分组 = 公开分组 + 管理员分配给该用户的专属分组。创建 Key 时仿 new-api 从下拉里单选一个分组（显示名称、描述和倍率），之后可以在令牌列表里修改。
- 用户自建的 Key 只有名称、分组和过期时间，限流取每用户 RPM / 并发，没有模型白名单和 Key 自身额度；正文记录跟随全局设置。
- 每次调用都会检查 Key 的分组是否仍对该用户可用；分组被删除、取消公开或从用户身上移除后，Key 返回 `403`，门户里标为「不可用」，改选分组后恢复。
- **开放门户前至少要建一个公开分组并勾选渠道和模型**，否则用户没有分组可选；`/v1/models` 与门户的模型列表页只列 Key 所在分组允许、且已配置倍率的模型。
- 请求开始时检查余额，结束时一次性扣费：扣减余额、累加已用额度和请求次数，同时累计到所用 Key 上，并分别写入用户与 Key 的每日用量。带 Key 的调用与内网一致，会先按输入估算与声明的输出上限预扣额度，可用额度不足以支付预扣时返回 `429`；鉴于预扣，总额度基本不会透支，但每日额度仍可能少量透支，余额显示为负数。
- 新用户赠送额度、每日签到（随机奖励区间，按服务器日期每天一次）都在设置页「用户门户」卡片配置，签到默认关闭。
- 调用记录来自请求日志，只给用户看元数据（不含请求和响应正文），按日志保留天数清理；删除 Key 后旧记录仍然可见。

### 管理

- **用户**页：按用户名搜索，查看余额、已用、请求数、Key 数、专属分组、注册与最近登录时间（悬停显示 IP）；可以启停、分配或移除专属分组、加减余额、重置密码、删除，展开一行可查看 Key 的分组，停用或删除该用户的 Key。管理员停用的 Key 会在门户里锁定，用户不能自行重新启用，只有管理员在管理端重新启用后才恢复；用户自己停用的 Key 仍可自行启用。
- 停用用户会立即让其登录会话和所有 Key 失效；删除用户会一并删除其 Key、会话、签到和每日用量，请求日志保留。
- 管理端请求日志里，门户用户的调用来源显示为「门户用户」，Key 标签为「门户用户名（Discord 用户名）/ Key 名」；Discord 用户名与门户用户名相同（忽略大小写、`.` 视同 `_`）时不重复显示。请求详情中单独显示 Discord 用户名。

### Discord 登录

门户的登录页与注册页可以显示「使用 Discord 登录 / 注册」，采用 Discord OAuth2 授权码流程：点击按钮后整页跳转到 Discord 授权页，授权完成后回跳到门户的 `/oauth/discord` 页面完成登录。该功能只面向门户普通用户，管理后台仍然只使用管理令牌。登录页调用 `POST /api/user/oauth/discord/start` 取得授权地址并写入 state Cookie，回跳页面用 `POST /api/user/oauth/discord/callback` 提交 `{ code, state }`，成功后写入登录 Cookie。

**注册开关：**

- 「开放注册」是总开关，关闭后用户名密码和 Discord 都不能新建账号，已有用户仍可登录。
- 子开关为「允许用户名密码注册」（`portal_password_register_enabled`，默认开启）和「允许 Discord 登录注册」（`discord_enabled`，默认关闭）。只关掉密码注册时，注册页只保留 Discord 按钮，可以用来做到「只能用 Discord 注册」。
- 同 IP 每日注册上限对两种注册方式共用；Discord 新建的账号同样获得「新用户赠送额度」。

**账号规则：**

- 已用 Discord 登录过的账号按 Discord 用户 ID 识别，直接登录；未注册过的自动建号。
- 门户用户名取 Discord 用户名（`.` 换成 `_`，不合法字符去掉，最长 20 位）；被占用时截短并加 4 位随机数字，最后兜底 `dc_` + 36 进制的 Discord ID。
- Discord 建的号没有密码，只能用 Discord 登录，个人中心不显示「修改密码」；管理员在用户页可以给这类账号「设置密码」，之后也能用用户名和密码登录。不支持给已有密码账号绑定 Discord，也不支持解绑。
- 用户页会在用户名旁显示 Discord 标签（Discord 用户名，悬停显示 Discord ID）；搜索框支持按 Discord 用户名模糊搜索和按 Discord ID 精确搜索。

**服务器列表记录：**

- Discord 登录始终申请 `identify guilds` 权限，每次登录用 `GET /users/@me/guilds` 取得用户所在的服务器（名称、ID、图标、是否服主、近似成员数），整体覆盖上次的记录，供管理员排查小号。之前只授权过 `identify` 的老用户，下次登录会重新看到一次 Discord 授权确认页。
- 获取服务器列表失败不影响登录，保留上次的记录；管理员停用的账号尝试登录时同样会更新记录。
- 管理后台用户页展开 Discord 用户的行即可查看服务器列表和记录时间，点服务器右侧的搜索按钮可以列出同在这个服务器的用户；搜索框支持按服务器名模糊搜索和按服务器 ID 精确搜索。管理端接口为 `GET /api/users/:id/discord-guilds`。
- 统计页的「服务器排名」按库内加入人数列出 Top 50 服务器，附带占已记录用户的比例和 Discord 给出的近似成员数；名称、图标取最近一次记录，不受时间范围和 Key 筛选影响。点右侧搜索按钮会跳到用户页列出这个服务器里的用户。管理端接口为 `GET /api/stats/discord-guilds`。
- 服务器图标直接从 Discord CDN 加载，浏览器连不上 Discord 时显示服务器名称首字。

**准入门槛（可选）：**

门槛由若干「规则组」组成（`discord_rules`），满足任一规则组即可登录；每个规则组包含一个或多个「服务器条件」，组内条件必须全部满足。每个服务器条件要求用户是该服务器成员（服务器开启成员审核时，未通过审核的成员不算满足），另有三类可选的身份组要求，留空不检查：

| 身份组要求 | 字段 | 含义 |
|---|---|---|
| 必须全部拥有 | `all_roles` | 列出的身份组一个都不能少 |
| 至少拥有一个 | `any_roles` | 列出的身份组至少有一个 |
| 拥有即拒绝 | `deny_roles` | 拥有其中任一个就不满足，可用来排除「禁言」「小号嫌疑」之类的身份组 |

例如「规则组 1：服务器 A 同时拥有『已验证』和『Lv5』，并且加入了服务器 B」或「规则组 2：服务器 C 拥有『管理员』」，满足其中一组就能登录。

- 设置了任何规则组时，Discord 登录会额外申请 `guilds.members.read` 权限（scope 为 `identify guilds guilds.members.read`），用 `GET /users/@me/guilds/{服务器 ID}/member` 查询成员信息。登录时先取用户的服务器列表，用户没加入的服务器直接按不满足处理，只查询加入了的服务器；服务器列表获取失败时逐个查询。
- 某个服务器的成员信息查询失败（网络错误、限流等）时，只要还有其他规则组满足就照常登录；所有规则组都没有满足、且有规则组因查询失败没法判断时，提示查询失败、请稍后再试，不会当作不满足条件。
- 被拒绝时的提示：所有规则组不满足的原因相同（都没加入服务器、都缺身份组等）时照原因提示，原因不同时提示不满足任何一组登录条件。
- 上限：最多 10 个规则组，每组最多 10 个服务器条件，全部规则最多涉及 20 个不同的服务器，每类身份组最多 50 个；同一规则组内服务器不能重复，不同规则组可以使用同一个服务器。
- 门槛只在登录时检查：用户退群或被撤销身份组后，已有的登录会话（30 天）和 API Key 不会立即失效，只是下次无法再用 Discord 登录。
- 获取服务器 ID、身份组 ID：Discord 设置 → 高级 → 打开开发者模式，右键服务器图标「复制服务器 ID」、右键身份组「复制身份组 ID」。只能填 ID，不能填名称，多个身份组 ID 用逗号或空格分隔。
- 旧版本的单服务器门槛（`discord_guild_id` + 拥有任一即可的 `discord_role_ids`）升级后自动迁移为一个规则组：该服务器的身份组填进「至少拥有一个」，旧设置项随即删除。

**配置步骤：**

1. 在 Discord Developer Portal 创建应用，在 OAuth2 页面取得 Client ID 与 Client Secret。
2. 在 Redirects 中添加回调地址 `{公网 Base URL}/oauth/discord`。管理后台设置页的「Discord 登录」卡片会显示并可复制该地址；没填公网 Base URL 时，回调地址跟随用户访问门户的地址，建议先填好公网 Base URL。
3. 在设置页填入 Client ID / Secret 并开启。开启时 Client ID 和 Secret 必须已填写，否则保存报错。
4. 请求 Discord API 走设置里的「HTTP 代理」（`proxy_url`），服务器在国内时需要配置代理。

### 会话与防刷

- 登录后发放 30 天有效的会话 Cookie（`HttpOnly`、`SameSite=Lax`、只发往 `/api/user`，HTTPS 反代下带 `Secure`），数据库只保存令牌的 SHA-256；修改密码会让其他设备的登录失效。
- 门户接口不开放跨域，写操作只接受 JSON 请求体，配合 `SameSite` 防止跨站请求伪造；页面带 `X-Frame-Options: DENY` 等安全响应头。
- 同一 IP 每天最多注册「同 IP 每日注册上限」个账号（默认 3，`0` 不限，IPv6 按 /64 统计）；登录失败与 `/v1` 鉴权失败共用公网 IP 失败计数，5 分钟内失败 10 次封禁 15 分钟，带有效 Key 的 `/v1` 调用不受封禁影响。登录另按用户名单独计数，IP 或用户名任一维度被封都拒绝登录；同一 IP 对同一账号最多同时进行 2 个密码校验。注册时遇到「用户名已被占用」也计入该 IP 的失败次数，被封禁的 IP 不能注册。修改密码按账号与 IP 各自计数，同一账号同时只处理一个改密请求。全站密码哈希并发上限为 2，避免占满线程池。客户端 IP 的取法见下文[反向代理与客户端 IP](#反向代理与客户端-ip)。
- 发起 Discord 授权时会生成随机 state，同时写进只发往 `/api/user/oauth/discord` 的 10 分钟 HttpOnly Cookie；回调时比对，保证只有发起授权的浏览器能完成登录，防止登录 CSRF。state 一次性使用，回调时无论成败都会清除。
- Discord 回调同样受 IP 鉴权失败封禁约束，state 不匹配计入失败次数。Client Secret 只保存在服务端，门户 `/api/user/status` 不下发。授权地址带 `prompt=none`，授权过的用户再次登录不会停在确认页。
- 门户没有验证码、邮箱验证和找回密码，忘记密码需要管理员在用户页重置；Discord 注册的账号没有密码。

## 请求预处理

在**预处理**页配置规则。提示词、工具过滤和参数规则可按渠道、客户端入口格式、请求模型、调用来源和指定 Key 限定范围，各维度同时满足才生效，留空表示不限。模型名使用映射前的客户端请求名称，按精确值匹配。

| 功能 | 能力与边界 |
| --- | --- |
| 提示词规则 | 可视化生成字面量规则或手写正则，替换文本留空可删除，也可设为命中即移除整条消息；支持角色范围和只处理最后 N 条消息 |
| 工具过滤 | 按工具名精确匹配黑名单，清理对应工具定义及相关历史调用 / 结果 |
| thinking 清理 | 仅在 Anthropic 同协议直通路径清理历史块，可保留最近 N 个 thinking / redacted_thinking 块；另有独立的 redacted 清理开关 |
| 参数修改 | 支持赋值、缺失时添加、存在时修改、删除及参数 JSON 正则替换；支持点路径、数组下标和 JSON 值 |
| 伪思考 | 将指定标签内的普通输出整理为 Anthropic thinking 块，并通过本地记录续接历史内容 |
| 跨格式思维链 | 配置推理密文暂存容量，以及转换到 Claude 时是否自动调整不兼容的推理 / 采样参数 |

处理顺序为：命中时恢复伪思考历史并注入指令 → 清理 thinking → 工具过滤 → 提示词规则 → 正则包 → 构造上游请求 → 参数规则。提示词规则、正则包和参数规则分别按列表顺序执行，每次渠道尝试重新判断作用范围。

提示词规则的动作设为**移除整条消息**时，消息文本命中查找内容，这条消息就不再发往上游，角色范围和深度的含义与替换时相同。Anthropic 的顶层 `system`、Responses 的 `instructions` 各算一条 system 消息；Claude 格式里嵌在 user 消息中的 `tool_result` 按 tool 角色单独判断，命中只移除该结果。被移除的内容带有工具调用或工具结果时，配对的另一半一并移除。网关不补位：规则移除了全部消息，或剩余消息的角色顺序上游不接受时，由上游返回错误。

### 正则包（高级模式）

**正则包**页是提示词规则的高级模式：把一组步骤打包成一个预设，整体启停、导入导出，用来成套改写某个客户端（如 Claude Code、Codex）自带的提示词。所有启用且命中范围的包按列表顺序依次执行，排在普通提示词规则之后。

**启用范围。** 除渠道、入口格式、模型、调用来源、指定 Key 外，正则包还有两项：

- **UA 白名单**：客户端 `User-Agent` 命中任意一条才启用，留空表示不限。条目默认按关键词包含匹配、不区分大小写（如 `claude-cli`）；写成 `/正则/flags` 时按正则匹配（如 `/^claude-cli\/2\./`）。设置了白名单后，不带 `User-Agent` 的请求不启用。
- **启用条件**：一条匹配系统提示词文本的正则，或一段返回布尔值的 JS 表达式。`User-Agent` 可以伪造，改版客户端也常沿用原来的值，按提示词特征识别更准。

**步骤。** 每个步骤有独立开关和可选的执行条件（JS 表达式，为假时跳过）。

| 步骤 | 作用 |
| --- | --- |
| 正则 | 查找替换，或命中即移除整条消息；「替换为」是模板，每个匹配渲染一次。除消息文本外，还可作用于工具定义的描述与参数说明 |
| 注入 | 把模板渲染出的文本加到系统提示词开头 / 结尾，或作为一条消息按深度插入；渲染结果为空时不注入 |
| 脚本 | 一段异步 JS，直接读写整个请求 |

**模板。** 支持类酒馆的宏与 EJS，完整列表见页面里的「语法速查」。

- 宏：`{{setvar::名::值}}`、`{{getvar::名}}`、`{{addvar}}`、`{{incvar}}`、`{{random::a::b}}`、`{{pick::a::b}}`、`{{roll::2d6}}`、`{{time}}`、`{{date}}`、`{{isodate}}`、`{{trim}}`、`{{newline}}`、`{{// 注释}}`，以及网关特有的 `{{model}}`、`{{ua}}`、`{{channel}}`、`{{key}}`、`{{system}}`、`{{lastUserMessage}}` 等。
- EJS：`<% 代码 %>`、`<%= 表达式 %>`、`<%# 注释 %>`，代码里可以 `await`。
- 正则步骤的替换模板里可用 `$1`、`$&`、`$<名字>` 引用捕获组。
- 只解析你写的模板本身。请求里原有的 `{{…}}` 和 `<% %>`、宏的取值、捕获组的内容都按普通文本处理，不会被执行；未知的宏原样保留。

**变量与参数。** 变量是请求级的：同一次请求里各包、各步骤共用，请求结束即丢弃，典型用法是前一步用正则把 harness 写进提示词的信息（如工作目录）抓出来，后面的模板再引用。包参数是包对外的设置项（文本 / 开关 / 数字），模板里用 `{{参数名}}` 或 `params.参数名` 读取，使用者改参数即可，不用动正则和脚本。

**脚本接口。** 脚本和 EJS 里可用 `req`（与格式无关的请求视图）、`body`（原始请求体）、`vars`、`params`、`ctx`（模型、UA、渠道、Key 等）。`req` 提供 `system`（可读写）、`prependSystem` / `appendSystem`、`messages`（每项有 `role`、可写的 `text`、`raw`、`remove()`）、`insert` / `append` / `remove`、`tools`（每项有 `name`、可写的 `description`、`schema`）。请求体有三种形状，`req` 在三者下用法一致，`ctx.shape` 给出当前形状：

| `ctx.shape` | 何时出现 | 结构 |
| --- | --- | --- |
| `anthropic` | Anthropic 入口 → Anthropic 上游直通 | 顶层 `system` + `messages` |
| `responses` | Responses 入口 → Responses 上游直通 | `instructions` + `input` |
| `chat` | OpenAI Chat 直通，或任何跨协议转换 | 中间表示，`system` 在 `messages` 内 |

**出错处理。** 模板或脚本抛错、超过 30 秒时，这一步不生效，后面的步骤照常执行，请求正常发往上游。脚本在请求体的副本上运行，成功后才写回，出错的步骤不会留下改了一半的结果。请求日志详情的「正则包」页签列出本次命中的包、每一步的状态（已改写 / 无改动 / 条件不满足 / 出错）、报错信息和 `console.log` 输出。

**试运行。** 「试运行」页签可以粘贴请求体 JSON，或从请求日志选一条（一并带出它的 `User-Agent`、模型和入口格式），在网关上执行当前未保存的包，查看改写前后的逐行对比、各步骤状态和最终变量值。试运行不请求上游、不写日志，但模板和脚本会真实执行。

> [!WARNING]
> 模板和脚本以网关进程的权限运行，没有沙箱：可以 `fetch`、`require`、读写文件。导入别人分享的正则包，等同于在这台机器上运行对方的程序，请只导入来源可信的包。导入的包默认不启用，带代码的包导入前会提示确认。

导出的文件不含渠道和 Key 的限定（这些 id 只在本机有意义）。「导入」也接受预处理页导出的普通规则数组，会转成一个只含正则步骤的包。

**参数规则作用于适配器构造完成后的最终上游请求体**，参数名应对应上游格式，可以删除适配器自动补充的字段。它主要面向非消息参数；消息、系统提示和由中继控制的字段有按协议设置的保护范围，消息内容改写应使用提示词规则。后置参数规则也可能重新添加前面删除的参数。

thinking 清理不用于跨格式 IR 路径；单独的 `redacted_thinking` 清理开关不继承普通 thinking 清理的渠道 / 模型范围。

修改后需要点击**保存修改**。提示词规则支持 JSON 导入 / 导出和单段文本预览；参数测试只试运行当前单条规则，不发送上游请求，也不模拟完整转换链路。

### 伪思考与思维链库

- 仅支持 **Anthropic 入口 → `anthropic` 类型渠道**的同格式路径；当前不支持 Vertex Claude 或跨格式路径。
- 需要开启“丢弃 thinking”、将保留数量设为 `0`，并同时命中 thinking 清理与伪思考的渠道 / 模型范围。
- 可配置起止标签和引导提示词；匹配到的标签文本会持续存入本地思维链库，后续根据客户端回传的签名自动恢复历史 assistant 内容。
- 这些内容来自模型输出的标签文本；网关生成的标识只用于本地续接，不具备上游原生 thinking 签名的认证能力。
- 思维链库用于查看和管理此类记录，无法给任意模型或任意请求自由注入库中条目。Responses 推理密文暂存属于另一类记录，不显示在该管理弹窗中。

## 协议转换与兼容边界

三种入口可路由至四类渠道；**同协议优先直通，跨协议尽力转换常用能力**。这里的直通仍会执行模型映射、已启用的预处理和必要的协议调整，SSE 也会经过解析重组。

### 通用能力

- 支持常用文本对话、函数工具定义 / 调用 / 结果、图片输入及可映射的流式增量。
- Anthropic 与 Responses 之间可转换部分文件内容字段；上游文件 ID 无法跨厂商自动解析或上传。Gemini 转换侧支持文本、图片和文件（base64 转 `inlineData`，URL 转 `fileData`），仅有文件 ID 的部件无法发给 Gemini；工具结果里的图片在 Gemini 3+ 放进 `functionResponse.parts`，更早的模型随工具结果单独追加。
- 多候选输出、复杂工具 Schema、音视频和厂商扩展字段不保证等价转换。`cache_control` 等缓存控制字段可能丢失；缓存 Token 计数的转换单独处理。
- 当前没有 Gemini 原生入口，也没有实现完整的 Responses 查询、取消、删除、Conversations 或 Files API。

### Responses 的状态与托管工具

- Responses → Responses 保留原生字段，由上游执行有状态会话及内置工具；模型映射和已启用的预处理仍会生效。
- Responses 转其他协议时，`previous_response_id`、`conversation`、`prompt`、`context_management`，以及 `item_reference` / `compaction` / `compaction_trigger` 输入项无法转换，会返回 `400`。
- 网关没有按 response ID 或 conversation 绑定渠道。选到不兼容渠道后也不会自动寻找另一个 Responses 渠道；有状态请求应固定到持有相应状态的 Responses 上游。
- Responses `web_search` 与 Claude `web_search_*` 的部分工具定义可以双向映射；搜索调用历史、结果块、引用及其他托管工具不保证转换。Chat 路径不消费这套托管工具定义；Gemini 路径在没有函数工具时把 `web_search` 映射为 `googleSearch`，与函数工具同时出现时丢弃。
- Responses `custom` 工具可在部分路径映射为函数参数包装，grammar 等约束不会完整保留。

### thinking / reasoning 往返

- Claude 与 Responses 间支持推理意图、可读思考、签名及推理密文的转换与历史回传；相关续接依赖客户端保留这些字段及本地暂存记录仍然存在。
- **跨格式构造 Responses 上游请求时**默认使用 `store: false`，并自动追加 `include: ["reasoning.encrypted_content"]`。显式 `store: true` 时不自动追加；Responses 同格式直通不会补这两个默认值。
- Responses 相邻的一组 reasoning 项会合并为一个 Anthropic thinking 块，遇消息或工具调用时分组；回传时利用本地记录尝试恢复原有项及顺序。
- 推理项含密文但没有可读摘要时，thinking 文本使用字符串 `"null"` 占位。暂存淘汰或无法匹配后继内容时，部分推理项无法恢复。
- Gemini 上游：推理意图映射为 `thinkingConfig`（Gemini 3+ 用 `thinkingLevel`，只发 LOW / MEDIUM / HIGH，3 Pro 的 MEDIUM 改发 HIGH；2.5 用 `thinkingBudget` 并按型号钳制范围），请求了推理时附带 `includeThoughts` 返回思考摘要；无法从模型名识别版本时不发 `thinkingConfig`。
- Gemini `functionCall` 上的 `thoughtSignature` 会封装进推理项签名（Anthropic / Responses 客户端随 thinking 块带回），同时按工具调用 ID 暂存在本地（OpenAI Chat 客户端只需带回 `tool_call_id`）；重建请求时挂回原 `functionCall`。签名缺失时 Gemini 3+ 使用官方占位签名跳过校验。带 Gemini 签名的 thinking 块发往 Claude 时会被剔除。
- 上游 `store: false` 不会关闭 AggHub 自身的日志和推理暂存；本地封装、哈希及压缩也不提供数据加密保护。

| 请求日志 | 条件筛选（含来源与 Key）、关键词搜索、分页、总耗时与首字延迟、正文详情、删除单条或清空全部请求日志 |
| 预处理 | 提示词、工具、thinking 与参数规则，预览及思维链库管理 |
| 正则包 | 提示词预处理的高级模式：成套的正则 / 注入 / 脚本步骤，UA 白名单与启用条件，宏模板与 EJS，试运行与导入导出 |
| 设置 | 入口地址、管理令牌、公网分发、用户门户、重试、超时、熔断、代理及日志留存 |

### 统计口径

- 总请求、成功率、Token 和平均延迟按**最终结果记录**统计，不累计中间重试尝试。
- 平均延迟取最终一次尝试的完整耗时：流式包含该次流的消费过程，不含此前尝试与重试等待；单个请求的总耗时（含重试等待）与首字延迟记录在请求日志中。
- usage 主要依赖上游返回，包含可识别的缓存读写等明细；缓存 Token 属于输入 Token 的子集，不能再次加到总量中。
- 图表展示请求量和 Token 趋势；成功率与平均延迟显示为概览指标。统计直接来自留存日志，删除或过期清理日志会改变统计结果。
- 点数按日志里记录的每次请求折算点数汇总。Key 的额度和每日用量另存在 `usage_daily` 表，不受日志清理影响，所以统计页的点数可能少于 Key 的已用额度。
- 门户可用性页的自动测活也是请求日志，会计入统计页的请求量、成功率与 Token。

### 日志查看

- 支持按状态、入口格式、流式与否、渠道、模型、调用来源和 Key 筛选；关键词搜索匹配模型、上游模型、渠道名、Key 名称、错误信息、门户用户名、Discord 用户名与客户端 IP（模糊匹配），以及 Discord ID、请求 ID（精确匹配），不搜索正文。关键词按字面匹配，`%`、`_` 不作为通配符；用户被删除后，无法再按其用户名或 Discord 信息搜到其日志。
- 每条日志记录调用来源、Key 名称快照、客户端 IP 和折算点数；删除 Key 后日志仍显示原名称。
- 流式请求还会记录首字延迟 `first_token_ms`（`INTEGER`，启动时自动补列）：从网关收到请求到开始向客户端输出第一个有效内容（正文 / 思考 / 工具调用）的毫秒数，包含预处理、失败重试与换渠道的等待，与列表「延迟」（总耗时）同口径。非流式请求、旧日志及首字前就失败的请求为空。列表的延迟列分两行显示总耗时与小字「首字 xxx ms」，详情元信息及「请求 ID · 总耗时 · 首字 · 最后尝试」一行中同样显示。
- 详情可查看对话、请求头、非消息参数、原始 / 改写后请求、网关响应、上游原始回复，以及存在时的历史思考注入记录。Responses 上游回复在日志中省略回显的 `instructions` / `tools`（与上游请求相同）及网关不使用的推理密文副本（`output_item.added` 与终态 `output` 中已由 `output_item.done` 记录过的项），被省略处写入 `[agghub 日志省略：…]` 占位，其余 SSE 帧逐字保留；转发给客户端的内容不受影响。
- 默认列表只展示最终结果；管理 API `GET /api/logs?include_retries=1` 可包含中间尝试。当前没有按请求关联的完整尝试链视图、日期范围筛选或文件导出功能。
- “清空日志”作用于全部请求日志和正文块，不受当前列表筛选条件限制。

## 数据存储、备份与安全

- 数据库位于 `data/agghub.db`，首次启动自动创建并启用 SQLite WAL；运行期间可能同时存在 `-wal` / `-shm` 文件，checkpoint 后 WAL 截回 4MB 以内。
- 请求日志元数据与正文都在同一数据库内。正文按 `(kind, SHA-256)` 去重，普通正文与 manifest 使用独立类型，避免相同文本混用影响 GC。适用时把 `messages` / `input` / `contents`（Gemini 上游请求体）等数组逐项切块，多轮对话的历史消息只存一份；新块使用 Zstd level 3，不支持时回退 gzip，较小内容可直接存储。
- 散块正文存放在独立的 `blob_data` 表，打包时整行删除，页面可整页释放给增量回收，不在块表内留下页内空洞。
- 超过 1 小时的冷块按时间顺序打包，普通正文与 manifest 分开成包：正文每包原文最多 16 MiB，不满 4 MiB 的尾部通常等待最早块满一天；manifest 每包最多 4 MiB，不满 1 MiB 时同样等待一天。每包最多 1024 个块，单块超过包上限时保持散块。冷包使用 Zstd level 6、16 MiB window、关闭 LDM，压缩及维护中的解压交给线程池。运行时不支持 Zstd 时不打包。
- 日志详情按标签加载正文，同次还原会复用共享消息。解压后的冷包使用最多 64 MiB 的 LRU 缓存，闲置一分钟释放；旧版本超大包可以读取，但不进入常驻缓存。管理接口 `GET /api/logs/:id` 保持完整详情兼容；`?fields=` 仅取元数据和 `available_fields`，`?fields=request_body,response_body` 只取指定正文，未加载字段省略、未保存字段为 `null`。
- 思维链暂存以签名中的 32 字节 SHA-256 摘要为主键，对外收发的签名不变；查询时按原算法复核整段签名。
- 门户通知保存在设置项 `portal_notice`；公告存放在独立的 `announcements` 表（id、content、extra、type、publish_at、created_at、updated_at），管理接口为 `GET` / `POST /api/announcements` 与 `PUT` / `DELETE /api/announcements/:id`，随 `data/` 目录一起备份。门户背景图与品牌图标存放在 `site_assets` 表。
- 当前版本不再自动迁移旧版存储布局（正文内嵌在 `blobs` 行内的块表、以签名文本为主键的暂存表）。检测到旧布局时服务启动报错且不修改数据库，需要先停服并离线转换，**转换前请先备份 `data/` 目录**。
- **含 Zstd 正文或打包块的数据库需要支持 Zstd 的 Node.js 才能读取相关记录**。恢复备份时尽量保持兼容的运行时版本，避免直接降级。
- 服务开始监听后启动维护，每分钟检查一次，单次最多删除 5000 条过期日志（每批 500 条），`log_retention_days` 为 `0` 时不删除；有过期日志删除时或距离上次 GC 超过 6 小时，原子回收无引用块。每轮最多写入 2 个冷包，时间预算 250 ms，已开始的单包处理完成后再让出；任务单飞运行，积压在后续轮次继续处理。稀疏包直接重写有效片段，不先还原为单独压缩块。关闭正文存储只影响后续写入，思维链暂存保持独立容量设置。
- 日常维护只增量回收少量空闲页并使用非阻塞 checkpoint。页内空洞可用 `npm run logs:storage` 只读检查；需要整库整理时，先停止服务，再执行 `npm run logs:storage -- --apply`。工具先取得独占锁并备份，再执行 `VACUUM`，备份默认保留在数据目录内的 `backups/`；可用 `AGGHUB_BACKUP_DIR` 指定目录，不自动删除备份。
- 备份时建议先停止服务，再复制整个 `data/` 目录。
- **内网端口默认无鉴权，请勿直接暴露到公网**。内网端口默认监听所有网卡，应配合可信内网和防火墙使用；静态页面和 `/api/health` 即使配置令牌也仍可访问。需要对外提供服务时，开启公网端口并只暴露公网端口。
- 管理接口可以读取上游凭证，管理令牌带有全部管理权限，不要发给别人；分发请使用令牌页创建的 Key。分发 Key 以明文保存在数据库中，请妥善保护数据库、备份及浏览器中的令牌。
- 日志只对部分认证头做服务端脱敏，请求 / 响应正文没有通用敏感信息过滤。提示词、工具参数和错误信息可能包含隐私内容，分享日志前请自行检查。

```text
│   └── styles/
│       ├── tokens.css           设计变量（颜色、圆角、阴影、字号，只有这里写色值）

```

## 开发与测试

```bash
npm run typecheck   # 服务端、管理端、门户、测试与脚本的类型检查
npm test            # 运行 server/test 下的全部单元 / 集成测试，可追加文件名片段筛选，如 npm test -- billing
```

- 每个测试文件在独立的临时数据目录中运行，不会读写实际的 `data/`；测试产物默认放在系统临时目录，可用 `AGGHUB_TEST_ROOT` 指定位置，运行结束后保留以便排查。
- 设置 `AGGHUB_TEST_QUIET=1` 时只输出每个文件的通过情况。
- 推送到 `main` 与提交 Pull Request 时，GitHub Actions 会自动执行类型检查与测试。
